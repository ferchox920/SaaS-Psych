# ADR: listados clínicos visibles en SQL

## Contexto

Los listados de pacientes y citas obtenían todos los registros del tenant y llamaban `CanAccessClient` una vez por registro. Para `N` filas se ejecutaban `1 + N` consultas de lectura, además de la auditoría. El filtrado posterior en Go también transfería filas no autorizadas al proceso.

## Decisión

El repositorio PostgreSQL ofrece `ListVisible` y `ListVisibleByRange`. Cada consulta conserva `tenant_id`, filtra con `EXISTS` las asignaciones vigentes `treating`/`supervisor` y las excepciones de lectura activas, y mantiene orden estable (`created_at DESC, id DESC` o `starts_at ASC, id ASC`). `EXISTS` evita duplicar filas si un usuario tiene más de una vía de acceso. La validación de acceso a una entidad individual permanece en el servicio.

La migración `000028` agrega índices parciales para ambos estados de archivo de pacientes y un índice `(tenant_id, starts_at, id)` para la agenda. Los índices de asignaciones y excepciones ya existían. La autorización sigue siendo independiente del rol: owner/admin tampoco recibe acceso clínico sin asignación o excepción.

## Verificación y alcance

`TestVisibleClientAndAppointmentListsPostgresIntegration` usa PostgreSQL real para verificar asignación, excepción, revocación, archivo y aislamiento entre tenants. Las pruebas de servicio `TestVisible*UsesSingleAuthorizedRepositoryRead` verifican una lectura autorizada y cero comprobaciones individuales. El patrón de consultas de la lista cambia de `1 + N` a una consulta SQL; la escritura de auditoría es adicional y no se incluye en ese recuento.

Los tres endpoints (`/clients`, `/clients/archived`, `/appointments`) ahora usan `limit` (50 por defecto, máximo 100) y `offset` (máximo 1.000.000); responden `next_offset: null` al terminar. El `LIMIT limit+1` se aplica **después** del filtro clínico y permite calcular si existe otra página sin una segunda lectura. Una prueba PostgreSQL verifica dos páginas sin filas ocultas entre ellas. Los selectores web recorren todas las páginas para preservar opciones completas; por tanto, cada respuesta y consulta es acotada, pero la carga total del selector aún crece con el número de pacientes. Para conjuntos grandes queda pendiente búsqueda remota/autocomplete.

El panel de resumen no necesita enumerar todas las páginas para mostrar sus tarjetas: lee una sola página visible (100 elementos como máximo) de pacientes y de citas del rango. Si hay otra página, muestra `100+` —un mínimo explícito, no un total inventado—. Una prueba de navegador devuelve una segunda página ficticia y verifica que el panel no la consulta; los selectores sí siguen recorriendo todas las páginas.

Medición ilustrativa local (PostgreSQL 16, base de demo pequeña, `EXPLAIN (ANALYZE, BUFFERS)`, 22-09-2026): la consulta de pacientes con `LIMIT 51` usó `clients_active_tenant_created`, devolvió una fila visible y ejecutó en **0,134 ms** (8 bloques en caché); la consulta de citas con rango de un año y `LIMIT 51` usó `appointments_tenant_starts_id`, devolvió dos filas visibles y ejecutó en **0,411 ms** (8 bloques en caché). El plan hizo un escaneo secuencial de 109 asignaciones para la muestra pequeña; no hay evidencia de rendimiento bajo carga ni comparación fiable de latencia antes/después. El beneficio probado es pasar de `1+N` lecturas de autorización a una lectura SQL acotada por página, más la escritura de auditoría.

`offset` permite repetir/omitir filas si se insertan o archivan registros entre páginas; el orden `(fecha,id)` sólo hace determinista cada instantánea. Al cambiar filtros o permisos, el consumidor reinicia el desplazamiento. Para recorridos transaccionales grandes se requiere un cursor keyset o snapshot. No se impone todavía un máximo de duración al rango de agenda; el tamaño de cada respuesta sí está acotado.

## Seguimiento de listados longitudinales

Una prueba instrumentada con trazas PostgreSQL reprodujo `ListDiffs` con **4 lecturas para 3 diffs** (`1+N`); ahora usa 2 lecturas, con operaciones asociadas por `diff_id` y filtradas por tenant y paciente. `ListEvents` y `ListHypotheses` presentaban el mismo patrón (**4 lecturas para 3 registros** incluso vacíos) y ahora cargan asociaciones de evidencia en una lectura adicional cada uno. `ListProcesses` ejecutaba **19 lecturas para 3 procesos vacíos**; ahora reúne eventos, hipótesis y estrategia por paciente y distribuye por identificador de proceso. La prueba de merge comprueba que las asociaciones de evidencia sobreviven al cambio.

Los enlaces de objetivos terapéuticos pasaron de **10 lecturas para 3 objetivos vacíos** a 2 lecturas mediante una consulta por lote filtrada por tenant y paciente. Tres metas con un indicador pasaron de **10 lecturas** a un máximo de 4; tres racionales de **7** a 2; tres versiones de GIRA con una fase cada una de **22** a un máximo de 6. Las pruebas también verifican la pertenencia de enlaces a su meta y versión GIRA. Quedan lecturas por entidad en rutas de detalle (`GetProcess`, `GetGIRA`) y la carga longitudinal completa todavía puede ser grande.

El listado de sesiones de un paciente ahora comparte `limit`/`offset` (50 por defecto, 100 máximo) y `next_offset` con los listados de pacientes y citas. La prueba PostgreSQL verifica el orden `started_at DESC,id DESC`, dos páginas y la ausencia de sesiones de otro paciente; la prueba HTTP verifica contrato y límite inválido. La UI recorre páginas hasta completar las opciones de sesión y conserva `can_write` de la primera respuesta. Cada consulta queda acotada, pero el cliente todavía agrega todas las sesiones en memoria.

`/clients/{id}/events`, `/clients/{id}/hypotheses`, `/clients/{id}/targets`, `/clients/{id}/goals`, `/clients/{id}/giras` y `/clients/{id}/processes` también ofrecen páginas (`limit` 50 por defecto, 100 máximo). Las consultas conservan sus órdenes anteriores; la carga de asociaciones se restringe a los identificadores de la página, incluidos eventos, hipótesis y estrategia de los procesos seleccionados. Pruebas PostgreSQL verifican dos páginas, aislamiento entre pacientes y asociaciones correctas; las pruebas HTTP comprueban límites y permisos; la UI muestra controles de página comprobados en navegador. Las migraciones `000030` a `000033` agregan índices para los órdenes de hipótesis, targets, goals y procesos; el orden GIRA ya tenía índice. El estado longitudinal completo todavía puede ser grande y cada proceso individual puede tener numerosas asociaciones. Para historias grandes faltan vistas resumidas y búsqueda remota; `offset` conserva la limitación ante escrituras concurrentes descrita arriba.

La sección `recent_events` del estado longitudinal filtra `approval_status='approved'` y aplica `LIMIT 20` en PostgreSQL, antes de cargar las asociaciones de evidencia. Una prueba con más de veinte eventos aprobados y otros propuestos más recientes verifica tanto el resultado como la consulta emitida. Las otras secciones del estado siguen siendo potencialmente grandes; este límite no convierte el estado completo en una vista paginada.

El estado también filtra en SQL los procesos aprobados, las hipótesis aprobadas sin proceso, la evidencia activa y las propuestas abiertas antes de cargar sus asociaciones. La carga de operaciones se restringe a los identificadores de propuestas seleccionadas. Las listas administrativas correspondientes conservan su alcance completo. Los procesos aprobados y las propuestas abiertas aún no tienen límite de cantidad en el estado; su tamaño depende de los datos del paciente.

La migración `000034` añade índices parciales para el evento aprobado más reciente, el orden de procesos aprobados, las hipótesis aprobadas sin proceso y las propuestas abiertas. La evidencia activa ya tiene un índice que comienza por tenant, paciente y estado. Una prueba PostgreSQL comprueba la definición real de los cuatro índices; no se atribuye una mejora de latencia sin una medición con una historia grande representativa.
